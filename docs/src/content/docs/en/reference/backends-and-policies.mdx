A `WorkloadSpec` describes *what* to run. Three fields shape how the platform runs it:

- **`backend`** — which serving engine launches the model.
- **`task_type`** — the modality the model serves (text, embeddings, audio, …).
- **`execution_policy`** — how the workload is scheduled and scaled.

Placement onto hardware is the platform's job — a `WorkloadSpec` has no `provider` and no `min_vram_gb`. You declare the workload; the platform reconciles it.

## Backends

The `backend` field selects the serving engine. In code you pass the `Backend` enum; on the wire it is a string.

| Backend enum | Wire string | When to use |
| --- | --- | --- |
| `Backend.OLLAMA` / `Backend.Ollama` | `ollama` | Quick local-style serving and broad GGUF model coverage. Simplest to stand up. |
| `Backend.VLLM` / `Backend.Vllm` | `vllm` | High-throughput production text generation. You control the launch command. |
| `Backend.VLLM_OMNI` / `Backend.VllmOmni` | `vllm-omni` | vLLM for multimodal / omni models. Same command-driven config as `vllm`. |
| `Backend.VLLM_EXL3` / `Backend.VllmExl3` | `vllm-exl3` | vLLM + ExLlamaV3 (EXL3 quantized weights) with host-memory MoE expert offload. `text2text` only; the config is only the `vllm serve` command. |
| `Backend.SGLANG` / `Backend.Sglang` | `sglang` | Structured / programmatic generation workloads on the SGLang runtime. |
| `Backend.LLAMACPP` / `Backend.Llamacpp` | `llamacpp` | Prebuilt `llama-server` for **GGUF** models (OpenAI-compatible). Strong on AMD/ROCm and Apple Silicon; `text2text` only. |
| `Backend.STABLE_DIFFUSION_CPP` / `Backend.StableDiffusionCpp` | `stablediffusioncpp` | stable-diffusion.cpp `sd-server` (OpenAI images surface `/v1/images/generations`), compiled for the worker's GPU at bootstrap. `text2image` only. |
| `Backend.STRATA` / `Backend.Strata` | `strata` | A big Mixture-of-Experts model (Qwen3.8-Flash-Next Coder 125B) on **one NVIDIA GPU**: hot experts stay in VRAM, the rest run from host RAM. OpenAI-compatible, so Claude Code works through `/v1/messages`. `text2text` only; the config is a `strata ...` command and an optional `strata_version`. See [Strata](#strata). |
| *(custom backend slug)* | `<your-slug>` | **Your own PyTorch model**, defined in Python and published to your tenant. Use when the model or its I/O doesn't fit a built-in. See [Custom backends](/en/guides/custom-backends/). |

<Aside type="note">
Python uses the `UPPER_SNAKE` members (`Backend.VLLM`); TypeScript uses the `PascalCase` members (`Backend.Vllm`). They map to the same wire strings shown above.
</Aside>

<Aside type="tip" title="Custom backends">
Beyond the built-ins, you can publish a **custom backend** — your own model as a small Python class (`setup()` loads it once, `process(job)` runs each request) — and target it from a `WorkloadSpec` by its slug (`backend="<your-slug>"`). Its I/O is a free JSON dict, not OpenAI-compatible, so any modality fits. It's private to your tenant. See the [Custom backends](/en/guides/custom-backends/) guide.
</Aside>

### Backend config

The `vllm` and `vllm-omni` backends are command-driven: you provide the `command` that launches the server, and optionally pin `vllm_version`. The backend-specific config on the wire is `{ command, vllm_version? }`.

<Tabs syncKey="lang">
  <TabItem label="Python">
```python title="vllm_workload.py"
from inferencekey import ManagementClient, WorkloadSpec, Backend

mgmt = ManagementClient.from_env(project="acme")

ref = mgmt.ensure(WorkloadSpec(
    name="support-bot",
    slug="support-bot",
    model="meta-llama/Llama-3.1-8B-Instruct",
    backend=Backend.VLLM,
    command="vllm serve meta-llama/Llama-3.1-8B-Instruct --max-model-len 8192",
    vllm_version="0.6.3",  # optional: pin the engine version
))
```
  </TabItem>
  <TabItem label="TypeScript">
```ts title="vllm_workload.ts"
import { ManagementClient, Backend } from "@inferencekey/sdk";

const mgmt = ManagementClient.fromEnv({ project: "acme" });

const ref = await mgmt.ensure({
  name: "support-bot",
  slug: "support-bot",
  model: "meta-llama/Llama-3.1-8B-Instruct",
  backend: Backend.Vllm,
  command: "vllm serve meta-llama/Llama-3.1-8B-Instruct --max-model-len 8192",
  vllmVersion: "0.6.3", // optional: pin the engine version
});
```
  </TabItem>
</Tabs>

<Aside type="tip">
`vllm_version` only applies to `vllm` / `vllm-omni`. The `command` is run verbatim by `vllm`, `vllm-omni`, and `llamacpp` — for `llamacpp` it must launch `llama-server` against a **GGUF** model (e.g. `llama-server -hf <repo> --hf-file <file.gguf> -ngl 99 -c 4096`). For `ollama` and `sglang`, leave `command` unset and let the backend launch the `model` you declared.
</Aside>

### Strata

A `strata` workload serves `text2text` on one NVIDIA GPU (Linux x86_64). Its config takes only two keys: `command` and the optional `strata_version`. The `command` is not a binary to run: it is a Strata pseudo-CLI that the worker turns into Strata's installer flags and engine config.

```
[ENV=VAL ...] strata --family <qwen|swift|coder|unsloth> --model <QUANT>
    [--context N] [--kv int8|q4_0|k8v4] [--parallel N] [--vram-reserve-mib N]
    [--pool-workers N] [other setup flags] [-- extra engine args]
```

- The head must be `strata` (after an optional `ENV=VAL` prefix). `vllm serve ...`, `llama-server ...` or `python -m serve.server ...` are refused.
- `--family` and `--model` pick the model. `--context`, `--kv` and the other setup flags go to Strata's installer.
- `--parallel N` serves N users together but turns speculative decoding off: one user is fastest without it. The worker never sets it for you.
- `--vram-reserve-mib N` and `--pool-workers N` go to the engine. With parallel slots and no reserve the worker adds `--vram-reserve-mib 1536` (the engine default pages VRAM with 8 slots). Without `--pool-workers` the worker sizes the CPU pool from the container CPU quota.
- Never pass `--port`, `--host`, `--api-key` or `--data-dir`: the worker owns them and strips them.
- Refused, never ignored: `--engine` (any value, also `mock`), `--gpus`, `--layer-split`, `--backend` other than `cuda`, `--experimental-speed-projection` other than `off`, and operations such as `--update`, `--rollback-engine`, `--check` or `--calibrate`.
- `strata_version` pins a release tag such as `v0.1.40` (never a branch). It is part of the runtime identity, so a new tag starts a new process.

| Recipe | `command` |
| --- | --- |
| Coder 125B IQ1_M, one user (speculative decoding) | `strata --family coder --model IQ1_M --context 262144 --kv int8` |
| Coder 125B IQ1_M, eight users | `strata --family coder --model IQ1_M --context 262144 --kv int8 --parallel 8 --vram-reserve-mib 1536` |

<Tabs syncKey="lang">
  <TabItem label="Python">
```python
from inferencekey import WorkloadSpec, Backend, ExecutionPolicy

spec = WorkloadSpec(
    name="Qwen3.8 Coder 125B on Strata",
    slug="strata-coder",
    model="qwen3.8-flash-next-coder-iq1_m",
    backend=Backend.STRATA,
    task_type="text2text",
    command="strata --family coder --model IQ1_M --context 262144 --kv int8",
    config={"strata_version": "v0.1.40"},  # optional release pin
    execution_policy=ExecutionPolicy.FIXED,
    worker_id="<your-worker-id>",
)
```
  </TabItem>
  <TabItem label="TypeScript">
```ts
import { Backend, ExecutionPolicy } from "@inferencekey/sdk";

const spec = {
  name: "Qwen3.8 Coder 125B on Strata",
  slug: "strata-coder",
  model: "qwen3.8-flash-next-coder-iq1_m",
  backend: Backend.Strata,
  taskType: "text2text",
  command: "strata --family coder --model IQ1_M --context 262144 --kv int8",
  config: { strata_version: "v0.1.40" }, // optional release pin
  executionPolicy: ExecutionPolicy.Fixed,
  workerId: "<your-worker-id>",
};
```
  </TabItem>
</Tabs>

The node needs a 24-32 GB NVIDIA GPU, at least 64 GB of RAM (about 126 GB or more for the full 125B model) and about 70 GB of fast NVMe. The first start downloads and builds about 60-70 GB, so wait with a long timeout (`wait_until_ready(timeout=3600)`). Throughput stays about 125-145 tok/s in aggregate from 1 to 8 users (measured on an RTX 5090): Strata does not scale up like vLLM batching. A runnable example is [`strata-qwen-coder-private-nvidia`](https://github.com/inferencekey/inferencekey-sdk/tree/main/examples/strata-qwen-coder-private-nvidia).

## Task types (modalities)

`task_type` declares the modality the workload serves. There are 12 task types; the default is `text2text`. The data-plane surface depends on the modality.

| Task type | Modality | Data plane |
| --- | --- | --- |
| `text2text` | Text in → text out (chat / completions). **Default.** | OpenAI-compatible chat/completions |
| `embedding` | Text in → vector out | OpenAI-compatible embeddings (`embed`) |
| `text2image` | Text in → image out | OpenAI-compatible |
| `text2audio` | Text in → audio out | OpenAI-compatible |
| `audio2text` | Audio in → text out (transcription) | OpenAI-compatible |
| `reranker` | Query + documents → ranked order | Async-only (no sync OpenAI route) |
| `classification` | Input → label / scores | Async-only (no sync OpenAI route) |
| `reward` | Input → scalar reward score | Async-only (no sync OpenAI route) |
| … | Additional modalities (12 total) | — |

<Aside type="caution">
`reranker`, `classification`, and `reward` are **async-only** — they have no synchronous OpenAI-compatible route. The synchronous `generate_text` / `generateText` and `embed` calls target `text2text` and `embedding` workloads.
</Aside>

## Execution policies

`execution_policy` controls how the workload is scheduled and scaled. There are three policies.

| Execution policy | Behavior | When to use |
| --- | --- | --- |
| `fixed` | Runs with a fixed allocation that does not scale. | Steady, predictable load; reserved capacity. |
| `scheduled` | Runs on a schedule. | Batch / periodic jobs; off-hours work. |
| `autoscaling` | Scales with demand. | Spiky or unpredictable traffic. |

<Aside type="note">
Policy-specific tuning is carried in `execution_policy_config`. Set `execution_policy` to one of `fixed`, `scheduled`, or `autoscaling`; pair it with `execution_policy_config` for the parameters that policy expects.
</Aside>

<Tabs syncKey="lang">
  <TabItem label="Python">
```python title="autoscaling_workload.py"
ref = mgmt.ensure(WorkloadSpec(
    name="support-bot",
    slug="support-bot",
    model="meta-llama/Llama-3.1-8B-Instruct",
    backend=Backend.VLLM,
    command="vllm serve meta-llama/Llama-3.1-8B-Instruct --max-model-len 8192",
    execution_policy="autoscaling",
    execution_policy_config={
        "min_workers": 0, "max_workers": 2, "max_hourly_cost_usd": 5.0,
        "workers": {"source": "cloud", "cloud_pool": {
            "gpu_pool": ["NVIDIA A100-SXM4-80GB"], "max_hourly_cost_usd": 5.0, "max_instances": 2,
        }},
    },
))
```
  </TabItem>
  <TabItem label="TypeScript">
```ts title="autoscaling_workload.ts"
const ref = await mgmt.ensure({
  name: "support-bot",
  slug: "support-bot",

    min_workers: 0, max_workers: 2, max_hourly_cost_usd: 5.0,
```

### `execution_policy_config` shapes

The policy *name* is the stable contract; `execution_policy_config` carries the per-policy parameters and is validated by the Manager. The keys below are the ones the Manager actually validates.

The Manager stores a normalized copy of the config (it fills in defaults such as `schema_version` and `max_in_flight` and expands GPU names), and also returns the config exactly as you sent it in `execution_policy_config_requested`. `ensure()` compares your spec with that field, so running it again with the same config sends no PATCH, whatever the policy. An older Manager that does not return the field makes `ensure()` compare with the normalized copy instead, which never matches a `scheduled` or `autoscaling` config: every run then sends a PATCH with the same values.

**`fixed`**: a constant allocation with no configurable fields. Omit `execution_policy_config`; the Manager stores it as:

```json
{ "schema_version": 1 }
```

**`scheduled`**: weekly time windows in a timezone, served by the `workers` you name. In the default `keep_queued` mode each rule lists `days` (`mon` to `sun`), `from` and `to` (`HH:MM`, a `to` earlier than `from` wraps past midnight) and the `min_workers` / `max_workers` while it is open; inside a window workers start when jobs queue up, and outside every window the workload drains to zero. `rules` must not be empty and `workers` is required (same `source` blocks as autoscaling below):

```json
{
  "mode": "keep_queued",
  "timezone": "Europe/Madrid",
  "rules": [
    {
      "days": ["mon", "tue", "wed", "thu", "fri"],
      "from": "08:00",
      "to": "20:00",
      "min_workers": 0,
      "max_workers": 2
    }
  ],
  "workers": {
    "source": "cloud",
    "cloud_pool": {
      "gpu_pool": ["NVIDIA A100-SXM4-80GB"],
      "max_hourly_cost_usd": 5.0,
      "max_instances": 2
    }
  }
}
```

**`autoscaling` (cloud)** — scales cloud workers between a floor and a ceiling. Worker bounds are `min_workers` / `max_workers` (**not** `min_replicas`/`max_replicas`). A cost ceiling `max_hourly_cost_usd` (> 0) is **required**, and `workers.cloud_pool` needs a non-empty `gpu_pool` of catalog display names:

```json
{
  "min_workers": 0,
  "max_workers": 5,
  "max_hourly_cost_usd": 5.0,
  "workers": {
    "source": "cloud",
    "cloud_pool": {
      "gpu_pool": ["NVIDIA A100-SXM4-80GB"],
      "max_hourly_cost_usd": 5.0,
      "max_instances": 5,
      "allowed_cuda_versions": ["13.0"]
    }
  }
}
```

`gpu_pool` entries are GPU display names from the cloud catalog (dashboard → **GPU Resources**). `allowed_cuda_versions` is an optional CUDA pin. A flat `gpu_pool` at the root is a legacy form that **cannot** carry `allowed_cuda_versions` — prefer the `workers.cloud_pool` shape above.

**`autoscaling` (private worker)**: scales across your own registered workers instead of cloud GPUs. `max_hourly_cost_usd` (> 0) is required here too, even when every worker is private:

```json
{
  "min_workers": 1,
  "max_workers": 4,
  "max_hourly_cost_usd": 5.0,
  "workers": {
    "source": "private",
    "private_worker_ids": ["wrk_7Yc2..."]
  }
}
```

<Aside type="note">
The config schema may gain fields over time, but these keys are what the current Manager validates. The [workloads guide](/en/guides/workloads-by-policy-worker-modality/) shows them in context per modality.
</Aside>

## Putting it together

`backend`, `task_type`, and `execution_policy` are independent fields on the same `WorkloadSpec`. Declare them together and call `ensure()` — drift is reconciled per [OnDrift](/en/reference/ondrift/).
